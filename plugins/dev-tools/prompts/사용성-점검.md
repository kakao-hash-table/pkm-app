프로젝트 {name}({path})의 화면 코드를 읽고 사용성·접근성 문제를 점검한다. 읽기만 한다. 파일을 고치거나 만들지 않고, 개발 서버를 띄우지 않는다.

순서:
1. README·package.json·폴더 구조로 화면 코드가 어디 있는지 찾는다(예: src/, app/, pages/, components/, web/, *.html, *.tsx, *.jsx, *.vue, *.svelte, 템플릿). node_modules·빌드 결과·생성 파일은 보지 않는다.
2. 사용자가 가장 많이 거칠 화면(첫 화면, 입력 폼, 목록, 설정)부터 읽는다.
3. 아래 기준으로 문제를 찾는다. 코드에서 확인한 것만 적고, 추측이면 "추정"이라고 쓴다.
   - 접근성(WCAG 2.2 AA 기본): 입력에 연결된 레이블, 이미지 대체 글, 아이콘만 있는 버튼의 이름, 키보드만으로 조작(클릭만 받는 div·span), 보이는 포커스 표시(outline 제거), 포커스 순서와 모달의 포커스 가두기, 색 대비가 낮아 보이는 색 조합(값을 보고 의심되면 대비 계산값을 적는다), 색만으로 전하는 상태, 터치 대상 크기(24px 미만), 제목 구조와 랜드마크, 동적 변화 안내(aria-live).
   - 닐슨 휴리스틱: 시스템 상태 보이기, 실제 세계의 말, 사용자 통제(취소·되돌리기), 일관성, 오류 예방, 기억보다 알아보기, 효율, 군더더기 없는 화면, 오류 알아보고 회복하기, 도움말.
   - 상태: 불러오는 중, 비었을 때, 실패했을 때, 권한 없음, 아주 긴 글·많은 항목일 때 화면이 어떻게 되는지. 없는 상태가 문제다.
   - 문구: 무엇을 하는 버튼인지 알 수 있는 동사, 개발 용어·코드 노출, 오류 메시지가 다음 할 일을 알려 주는지, 같은 것을 다른 말로 부르는지.
   - 파괴적 동작(삭제·초기화)에 확인이나 되돌리기가 있는지.
4. 같은 원인의 문제는 하나로 묶는다.

마지막 답은 이 형식으로:
요약: 전체 인상 한두 문장과 가장 먼저 고칠 것
문제(심각도 높은 순, 10개까지):
1. [높음|중간|낮음] 한 줄 제목
   위치: 파일:줄
   왜: 누가 어떤 상황에서 막히는지(관련 기준 — 예: WCAG 2.4.7, 닐슨 1번)
   고치기: 구체적인 수정(바꿀 코드나 문구를 짧게)
잘된 점: 지키고 있어서 유지할 것 한두 개
못 본 것: 코드만으로 판단할 수 없어 사람이 화면에서 볼 것(실제 색 대비, 화면 읽기 프로그램 동작 등)
